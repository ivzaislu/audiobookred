# Готовность к подключению второго источника

Дата аудита: 2026-08-02. Проверена архитектура версии 0.21.2.

## Итог

Проект **частично готов** к второму источнику.

Слой хранения и значительная часть очередей уже используют ключ `source`, поэтому
добавление второго торрент-источника не требует новой основной таблицы каталога.
Однако ingestion-слой, регистрация сервисов, API-маршруты и эксплуатационные
скрипты по-прежнему собраны вокруг конкретных классов RuTracker.

Практическая оценка:

- хранение и поиск: готовы;
- общие очереди и runtime-настройки: в основном готовы;
- подключаемый адаптер источника: не готов;
- эксплуатация нескольких источников: не готова.

## Что уже пригодно

1. `audiobook_releases` хранит `source` и `source_id`, а уникальность задана по
   паре `(source, source_id)`.
2. REST-поиск и фасеты поддерживают фильтр по источнику.
3. Таблицы `source_crawl_state`, `source_crawl_control`,
   `source_crawl_runs`, `source_crawl_jobs` и `source_job_events`
   разделяют данные по ключу `source`.
4. `SourceJobRepository` принимает ключ источника почти во всех операциях.
5. CLI строит адрес как `/api/v1/sources/$SOURCE`, поэтому его внешний формат
   уже рассчитан на несколько источников.
6. `source_runtime_settings` имеет отдельную строку для каждого источника.

## Что блокирует второй источник

1. В `Program.cs` напрямую регистрируются `RuTrackerClient`,
   `RuTrackerCrawler`, парсеры, Atom- и magnet-компоненты. Реестра источников
   или общего контракта модуля нет.
2. Все управляющие API-маршруты вручную объявлены под
   `/api/v1/sources/rutracker/...`.
3. `SourceSettingsRepository` зависит от `RuTrackerSourceDefinition`, поэтому
   значения по умолчанию любого нового источника сейчас фактически будут
   значениями RuTracker.
4. `SourceCrawlRepository` частично общий, но методы чтения и обновления листинга
   используют `RuTrackerSearchItem` и местами жёстко подставляют ключ
   `rutracker`.
5. Очередь предполагает модель `category_id + page`. Она хорошо подходит для
   форумных трекеров, но RSS-, REST- или cursor-based источник потребует
   адаптации задания.
6. Таблицы и workers для topic, Atom и magnet названы и реализованы как
   RuTracker-компоненты.
7. `install.sh`, cron, doctor и имена логов управляют только RuTracker.
8. Тесты не содержат contract-suite, которую обязан пройти любой новый
   источник.

## Рекомендуемая граница следующего архитектурного патча

Перед реализацией второго источника нужен отдельный патч источниковой границы:

- `ISourceModule` — ключ, возможности, категории и значения по умолчанию;
- `ISourceCrawler` — discover, enqueue, work, status, settings и maintenance;
- `ISourceRegistry` — разрешение модуля по ключу;
- единый набор endpoint-ов `/api/v1/sources/{source}/...`;
- source-specific DTO преобразуются в общие listing/detail records до записи
  в общие repositories;
- `SourceSettingsRepository` получает defaults от выбранного модуля;
- cron генерируется из списка включённых источников;
- общая contract-suite проверяет bootstrap, incremental, retry,
  дедупликацию и изоляцию данных двух источников.

## Выбор второго источника

Самый безопасный первый кандидат — источник с такой же моделью:

- числовые категории;
- постраничный листинг;
- стабильный идентификатор темы;
- отдельная страница деталей;
- magnet/info-hash.

Для RSS или cursor-based API сначала следует обобщить payload задания, иначе
новый адаптер будет вынужден имитировать `category_id + page`.

## Вывод

Основную схему каталога переписывать не требуется. Но добавлять второй источник
непосредственно копированием классов RuTracker не следует: это закрепит
дублирование в API, настройках и эксплуатации. Сначала нужна источниковая
граница, после неё второй форумный торрент-источник станет локальным адаптером.
